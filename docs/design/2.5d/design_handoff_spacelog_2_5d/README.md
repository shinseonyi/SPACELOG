# Handoff: SPACELOG 2.5D 디자인 적용

대상 레포: `shinseonyi/SPACELOG` (팀 레포 `delightPIP/teamproject`의 포크)
대상 브랜치: `SPACELOG-2.5D`
기준으로 읽은 코드: `main` @ 2026-11-12 (이 문서를 쓸 때 `SPACELOG-2.5D` 브랜치는 원격에서 보이지 않아 `main`을 읽었습니다. 브랜치가 `main`에서 갈라졌다고 가정합니다.)

## 1. 개요

팀이 만든 SPACELOG(수집 앱 + 로컬 웹)에, 디자이너가 HTML 시안으로 고치고 추가한 디자인과 기능을 적용합니다.
바뀌는 것은 세 가지입니다.

1. **시각 언어 교체**: 지금의 `docs/DESIGN.md` 스타일(보라 우주, 노랑·분홍, 3px 테두리, Black Han Sans)을 어두운 단색 스타일(검정 바탕, 반투명 어두운 카드, 포인트 컬러 하나, Pretendard)로 바꿉니다.
2. **우주 홈 재구성**: 2.5D 보기(기본)와 3D 보기 전환, 왼쪽 아래 카드 묶음, 오른쪽 목록 창.
3. **기능 추가·변경**: 별자리(기록 묶음 + 관측 목적), 관측소(새 화면, 탐사선과 함께 둠), 블랙홀(행성 삭제·복구), 행성 수정, CSV 대시보드, 체험 가이드 등.

### 1-1. 디자인 의도

구현 중 시안과 코드가 부딪히면, 아래 의도를 지키는 쪽으로 판단합니다.

**우주는 꾸밈이 아니라 "기록 공간"입니다.**
우주 컨셉을 스타일로만 쓰지 않고, 기록이 쌓이고 이어지는 하나의 공간이라는 뜻을 전하려고 몰입감 있는 구조로 설계했습니다. 그래서 웹은 우주 홈이 항상 바탕에 있고, 나머지 화면은 그 위에 열립니다.

**2.5D와 3D는 보는 깊이를 고르는 장치입니다.**
- 2.5D(기본): 더 간단하게 봅니다. 한눈에 훑고 정리할 때 씁니다.
- 3D: 더 깊이감 있게 봅니다. 공간 안을 날아다니며 둘러볼 때 씁니다.

두 보기는 같은 데이터와 같은 화면 구성을 다르게 보여 줄 뿐입니다. 어느 쪽에서도 같은 기능을 쓸 수 있어야 합니다. (화면 캡처는 3D 한 장만 두었고, 2.5D도 같은 구성입니다.)

**행성의 모습은 기록의 성격을 보여 줍니다.**
| 모습 | 뜻 |
|---|---|
| 기본 행성 | 일반적인 기록 모음 |
| 고리 | 다양하게 연결될 수 있는 행성 |
| 성운 | 아직 구체화되지 않은 기록. 개수는 "기록"이 아니라 "조각"으로 셉니다 |

**별자리는 사용자가 직접 묶는 그룹입니다.**
북마크 그룹과 비슷합니다. 서로 다른 행성의 기록이나 같은 행성의 기록을 사용자가 골라 묶고, 이름과 관측 목적을 붙입니다. 행성은 기록이 어디에 놓였는지를, 별자리는 사용자가 어떤 뜻으로 묶었는지를 나타냅니다.

**관측소는 기록을 "묶어서" 보는 곳입니다.**
기록을 하나씩 열어 보는 데서 그치지 않고, 별자리로 묶은 기록을 한곳에서 봅니다.
- 별자리 관측: 메모, txt, CSV, 이미지를 모아 봅니다. CSV는 시각화해서 봅니다.
- 재발견 혜성 관측: 아래 "재발견은 혜성입니다"를 참고하세요.

탐사선(기록을 실어 텍스트로 묶어 복사하는 기능)은 관측소와 목적이 다른 별개의 핵심 기능입니다. 관측소가 대체하지 않습니다.

**재발견은 알림으로 끝나지 않고 "혜성"입니다.**
오래된 기록이 다시 찾아온다는 뜻으로 "혜성"이라는 의미를 줬습니다. 우주 홈의 혜성 카드와 수집 앱의 OS 알림에서 끝나지 않고, 관측소의 "재발견 혜성 관측"에서 전체를 한꺼번에 볼 수 있습니다.

**한 줄로 줄이면:** 기록을 모으고(수집), 묶고(별자리), 다시 만나는(재발견·관측) 과정을 하나의 공간에서 이어서 경험하게 합니다.

## 2. 이 폴더의 파일에 대해

`design/` 안의 파일은 **HTML로 만든 디자인 참고물**입니다. 의도한 모습과 동작을 보여 주는 프로토타입이지, 그대로 가져다 쓸 제품 코드가 아닙니다.
할 일은 이 시안을 **레포의 기존 환경**(React 19 + Three.js + Vite + TypeScript + Zustand, `web/`; Electron, `apps/collector/`)에서 기존 패턴대로 다시 구현하는 것입니다.

- 시안은 `*.dc.html`이라는 형식입니다. 파일 위쪽의 템플릿(HTML + 인라인 스타일)과 아래쪽 `class Component`(로직)를 읽으면 됩니다. `{{ 이름 }}`은 로직의 `renderVals()`가 돌려주는 값입니다.
- 시안의 데이터는 전부 브라우저 `localStorage`와 예시 데이터(`spacelog-data.js`)입니다. 제품에서는 `apps/server`의 API와 `web/src/state/store.ts`로 옮겨야 합니다.
- 브라우저로 열어 보려면 `design/` 폴더를 정적 서버로 띄우고 `SPACELOG_Collector.dc.html`(수집 앱) 또는 `SPACELOG_Prototype.dc.html`(웹)을 엽니다.

## 3. 충실도

**High-fidelity.** 색, 글자, 간격, 문구, 상호작용이 최종 의도입니다. 값은 `design/design.md`와 각 시안의 인라인 스타일을 그대로 따릅니다.
단, 3D 보기의 행성 배치·카메라 수치는 시안에서 눈으로 맞춘 값이라 제품의 Three.js 장면(`web/src/universe/`)에 맞게 조정해도 됩니다.

### 4-1. 개발 영향 요약

디자인 교체만이 아니라 **서버와 공유 타입에도 변경이 필요합니다.** 아래는 개발 경험이 적은 사람도 읽을 수 있게 쓴 요약입니다.

#### 구조 한눈에 보기 (식당에 빗대면)

| 레포의 부분 | 하는 일 | 식당에 빗대면 |
|---|---|---|
| 웹 (`web/`) | 사용자가 보고 누르는 화면 | 손님이 앉는 **홀** |
| 로컬 서버 (`apps/server/`) | 기록을 저장하고 꺼내 주는 일 | **주방과 창고** |
| 공유 타입 (`packages/shared/types.ts`) | 웹과 서버가 주고받는 데이터의 모양을 적어 둔 약속 | 홀과 주방이 같이 보는 **주문서 양식** |
| 수집 앱 (`apps/collector/`) | 기록을 끌어다 놓는 PC 앱 | 식재료를 **들여오는 입구** |

기술은 웹이 React·Three.js·Vite·Zustand, 수집 앱이 Electron, 서버가 TypeScript(Node)입니다. 서버는 수집 앱 안에서 같이 실행되고, 기록은 사용자 PC의 보관함 폴더에만 저장됩니다. 클라우드 서버는 없습니다(Render에는 다운로드 안내 페이지만 올라갑니다).

#### 서버와 공유 타입까지 바꿔야 하는 이유

1. **새 기능은 "저장"이 필요한데, 저장은 서버만 합니다.**
   별자리를 만들고, 행성 색과 위치를 바꾸고, 행성을 블랙홀에 넣는 일은 전부 "나중에 다시 열어도 남아 있어야 하는 정보"입니다. 웹 화면만 만들면 홀(화면)은 생기지만 창고(저장 공간)가 없어서, 새로고침이나 앱 재시작 때 사라집니다.
   시안이 잘 동작하는 것은 브라우저의 임시 저장(`localStorage`)에 넣었기 때문입니다. 시안용 방법이라 제품에서는 서버 저장으로 옮겨야 합니다.
2. **웹과 서버가 같은 양식을 써야 합니다.**
   별자리나 행성 색 같은 새 정보를 주고받으려면 주문서 양식(`types.ts`)에 새 항목을 먼저 적어야 합니다. 양식을 고치지 않고 웹과 서버를 따로 고치면 서로 다른 모양으로 말하게 되어 오류가 납니다. 이 때문에 공유 타입을 먼저 바꾸고 웹과 서버가 그것을 따릅니다.
3. **서버가 해야만 하는 일이 있습니다.**
   CSV 파일을 넣을 때 열과 행을 읽어 두는 일, 웹에서 파일을 올리는 일, 보관함의 기록 파일을 다루는 일은 브라우저가 아니라 서버(PC 쪽)에서 해야 합니다.

#### 왜 "포크에서" 바꿔도 되는가

- 이 브랜치는 팀 레포의 **복사본(포크)**입니다. 복사본에서 고치면 팀의 원본 코드는 그대로입니다. 서버를 마음 놓고 실험할 수 있습니다.
- 팀 원본에 반영하려면 나중에 합치기 요청(PR)을 보내고 팀이 검토합니다. 그때 서버 변경이 많으면 팀(서버 담당)과 충돌이 날 수 있으므로, 변경 범위를 미리 팀과 맞추는 것이 좋습니다.
- 반대로 **웹만 바꾸는 방법**도 있습니다. `web`의 `npm run dev:mock`으로 가짜 데이터(`mocks/api`의 JSON)를 써서 화면을 먼저 완성하는 방식입니다. 시연과 디자인 확인에는 충분하지만 저장이 되지 않으므로 실제 제품으로는 쓸 수 없습니다.

#### 주의할 점

(아래는 서버를 바꾸는 경우의 주의점입니다. 지금은 시연용으로 서버를 바꾸지 않기로 했습니다. 아래 "결정 기록" 참고.)

1. **기존 데이터 이전.** 보관함(DB)에 항목을 추가할 때, 이미 쓰고 있던 사용자의 기록이 깨지지 않게 옮겨야 합니다. 특히 행성 색이 `planet-1~8`(생긴 순서)에서 사용자가 고르는 7색으로 바뀌는 부분이 그렇습니다. 서버를 바꾸게 되면 `apps/server/vault/db.ts`를 읽고 이전 계획부터 세웁니다.
2. **바뀌지 않는 것.** 탐사선(`cargo` 계약), 내보내기 API(`POST /api/export`), 재발견을 고르는 규칙(서버의 `rediscovery/pick.ts`)은 그대로 씁니다.
3. **목업도 같이 고칩니다.** 서버에 새 필드가 생기면 `mocks/api`의 JSON에도 넣어야 목업 모드가 동작합니다.

#### 결정 기록 (2026-11-12)

**시연용으로 먼저 진행합니다. 서버(`apps/server/`)와 공유 타입(`packages/shared/`)은 바꾸지 않고, 화면을 먼저 완성합니다.** 완성한 화면을 가지고 서버 담당자와 논의한 뒤, 서버 변경 여부와 범위를 정합니다.

| 항목 | 결정 |
|---|---|
| 서버·공유 타입 | **수정하지 않습니다.** 10장의 5단계(서버·공유 타입)는 보류합니다 |
| 새 기능의 데이터 | 웹 안에서만 다룹니다. 시안처럼 브라우저 저장(`localStorage`)에 두고, 목업 모드(`npm run dev:mock`)로 동작시킵니다 |
| 새 데이터 타입 | 공유 타입을 건드리지 않도록 `web/` 안에 따로 정의합니다 (예: `web/src/demo/`). 나중에 서버 담당자와 합의한 뒤 `packages/shared`로 옮깁니다 |
| 새 기간("이번 달", "전체") | 웹에서 날짜 범위(`custom`)로 바꿔 서버에 요청합니다. `PeriodPreset`은 바꾸지 않습니다 |
| 목업 데이터 | 새 기능에 쓸 예시 데이터는 `mocks/api`가 아니라 `web/` 안에 둡니다 (`mocks/api`는 서버 계약의 기준 문서이기도 해서 건드리지 않습니다) |
| 2.5D 렌더러 | DOM/CSS (시안과 같은 방식이라 옮기기 쉽습니다. 3D는 기존 Three.js를 그대로 씁니다) |

**이 방식의 한계 (시연용이라는 뜻)**
- 새 기능(별자리, 행성 색·모양·위치, 블랙홀, CSV 대시보드, 웹에서 기록 넣기)은 **이 브라우저에만 저장됩니다.** 다른 브라우저나 다른 PC에서는 보이지 않고, 브라우저 데이터를 지우면 사라집니다.
- 실제 서버에 연결하면 기존 기능(기록 보기, 탐사선, 재발견, 내보내기)은 동작하지만 새 기능은 서버에 저장되지 않습니다. **새 기능은 숨기지 않고 "시연용" 표시와 함께 보여 줍니다**(결정: 2026-11-12). 표시 방식(작은 알약 라벨 등)은 새 기능이 처음 들어가는 단계에서 정하고 확인받습니다.
- 서버가 읽어 줘야 하는 CSV 내용은 시연에서는 웹이 직접 읽습니다. 시안의 한도(12열·300행)를 그대로 씁니다.

#### 서버 담당자와 논의할 내용

완성한 시연 화면을 보여 주며 아래를 이야기합니다. 화면의 어느 부분이 서버 변경을 필요로 하는지는 위 "서버·공유 타입에 새로 필요한 것" 표와 7장을 함께 보면 됩니다.

1. **범위 합의:** 새 기능을 팀 원본 제품에 넣을지, 포크의 시연용으로 둘지. 넣는다면 어디까지(별자리, 블랙홀, CSV 대시보드, 웹에서 기록 넣기 등)인지.
2. **데이터 저장 방식:**
   - 별자리와 행성 모습(색, 모양, 좌표)을 보관함 DB에 어떻게 저장할지.
   - 이미 쓰고 있는 사용자의 보관함 데이터를 깨지 않고 옮기는 방법(DB 이전).
   - 행성 색이 `planet-1~8`(생긴 순서)에서 사용자가 고르는 7색으로 바뀌는 것을 받아들일지.
3. **블랙홀(행성 보관):** 행성을 지우지 않고 보관하는 방식(`trashedAtUtc`)과, 지금의 "빈 행성만 삭제" 규칙(SPEC 1-6)을 어떻게 정리할지. 보관 중인 행성의 기록을 목록·개수·재발견·내보내기에서 어떻게 다룰지.
4. **CSV 내용 읽기:** 서버가 CSV를 넣을 때 열·행을 읽어 둘지, 한도(12열·300행), 저장 위치, 조회 API(`GET /api/stars/:id/table`).
5. **웹에서 기록 넣기:** 지금은 수집 앱만 `POST /api/stars`를 부릅니다. 웹도 부르게 해도 되는지, 보안 규칙(POLICY 1-3의 Host·Origin·토큰 검사)에 영향이 없는지.
6. **기간:** `PeriodPreset`에 `month`, `all`을 추가할지, 아니면 웹에서 날짜 범위로 바꾸는 지금 방식을 유지할지.
7. **재발견·탐사선·내보내기:** 바꾸지 않는 것으로 정리했습니다. 맞는지 확인합니다. (재발견 선정 규칙 `rediscovery/pick.ts`, 내보내기 `POST /api/export`, `cargo` 계약.)
8. **공유 타입 변경 절차:** `packages/shared/types.ts`는 웹과 서버가 같이 쓰므로, 누가 언제 바꾸고 어떻게 검토할지.
9. **합치는 방법:** 포크의 변경을 팀 원본에 합치기 요청(PR)으로 보낼 때 단위를 어떻게 나눌지(디자인 교체 / 웹 새 기능 / 서버 변경을 따로 보낼지).
10. **문서:** `docs/SPEC.md`, `docs/DESIGN.md`, `docs/PRD.md`와 어긋나는 점(4장 표)을 팀 문서에 어떻게 반영할지.

- **재발견 혜성 관측**: 모든 행성에서 넣은 지 7일이 넘은 기록을 가까운 날짜순으로(최대 60). 정확히 7일 전 기록에 "오늘의 재발견" 표시.

## 7. 상태와 데이터 (새로 필요한 것)

`packages/shared/types.ts`와 `apps/server`에 아래가 추가돼야 합니다. 시안의 구현은 `design/spacelog-data.js`의 `reduce()`(액션 목록)와 `localStorage` 키들을 참고하세요.

| 새 개념 | 필요한 필드·API |
|---|---|
| 별자리(Link) | `{ id, name, memo(관측 목적), starIds[], viz: { mode: 'dash'|'table'|'photos'|'texts', chart: 'bar'|'donut', csvId?, cat?, val?, agg?, hide? }, createdAtUtc }`. 생성 / 이름·목적 수정 / 기록 넣고 빼기 / 풀기. 기록이 삭제되면 별자리에서도 빠지고, 빈 별자리는 없어집니다 |
| 행성 모습 | `Planet`에 `color`(7가지 중 하나), `shape: '' | 'ring' | 'nebula'`, `x`, `y`(우주 위 좌표), `editedAtUtc` |
| 블랙홀 보관함 | 행성 soft delete: `trashedAtUtc`. 보관 / 꺼내기 / 완전히 삭제 API. 보관 중인 행성의 기록은 목록·개수에서 빠집니다 |
| CSV 내용 | CSV 파일을 넣을 때 서버가 열·행을 읽어 둡니다(시안 한도: 12열 · 300행). `GET /api/stars/:id/table` 같은 조회가 필요합니다 |
| 기간 | `PeriodPreset`에 `month`, `all` 추가 (`packages/shared/period.ts`) |
| 웹에서 기록 넣기 | 웹의 "기록 넣기"(파일 드롭, 메모). 지금은 수집 앱만 `POST /api/stars`를 부릅니다 |
| 개인 화면 설정 | 2.5D/3D 선택, 숨긴 별자리 목록, 오른쪽 창 탭: 브라우저 저장으로 충분 |

`web/src/state/store.ts`에 추가할 것(이름은 제안):
- `view: '2.5d' | '3d'`, `sideTab: 'rec' | 'planet' | 'link' | null`, `links: Link[]`, `hiddenLinkIds: string[]`, `picked: string[]`(목록에서 체크한 기록), `obs: { open, mode: 'comet' | 'link', linkId | null }`, `editPos: boolean`, `trash: Planet[]`.
- 탐사선 계약(`cargo` · `addToCargo` · `removeFromCargo` · `exportFormat` · `openProbe`)은 **그대로 둡니다**. 관측소용으로 `openObservatory(linkId?)`를 새로 추가합니다. 관측소의 "AI용 텍스트 복사"도 내보내기 API(`POST /api/export`)를 씁니다.
- 기존 계약 `flyToPlanet` · `openPanel` · `openStar` · `closePanel` · `goBack` · `setPeriod`는 그대로 씁니다. `goBack` 순서에 관측소를 넣습니다: 탐사선·관측소 → 상세 → 패널 → 조망.

## 8. 상호작용 요약

- 행성 클릭 또는 목록 줄 클릭 → 카메라 이동(약 800ms) → 패널 열림(약 850ms 뒤).
- Esc: 한 단계씩 뒤로. 입력 중에는 무시.
- 2.5D 키: W·A·S·D와 드래그 = 화면 이동, Space = 축소, Shift = 확대, E = 가까운 행성에 착륙. 패널이 열려 있으면 받지 않습니다.

- 토스트: 흰 알약, 검정 글자, 약 2.4초. 기존 `ui/Toast.tsx`의 4초 규칙과 맞추세요.
- 재발견 알림: 수집 앱의 OS 알림(기존) + 웹의 혜성 카드. 누르면 그 기록의 행성으로 이동한 뒤 기록 상세.

## 12. 알려진 한계 (시안)

- 시안의 저장은 모두 브라우저 `localStorage`입니다. 여러 번 고치며 생긴 복구 코드(예: `spacelog_reset_1112`, "복구된 행성")는 제품에 옮기지 않습니다.
- CSV 열 성격 추정은 규칙 기반이라 틀릴 수 있습니다(연도·등급·평점 등). 사용자가 "쓸 열"에서 고칠 수 있어야 합니다.
- 3D 보기의 이름표 겹침 처리는 화면 좌표 충돌 검사로 했습니다. 제품의 `Scene.ts`에 이미 이름표 처리가 있으면 그것을 씁니다.
- 낮은 창(높이 540px 안팎)에서 요소가 빽빽합니다. 최소 지원 높이를 팀에서 정하세요.
- 접근성: 토글·체크에 `role`과 `aria-*`를 넣었지만 키보드만으로의 전체 흐름은 검수하지 않았습니다.
